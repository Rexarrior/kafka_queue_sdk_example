# Проверка параллельности на настоящем Kafka

Изолированный acceptance-стенд для бизнес-операции `logic.kafka_service.echo_payload`.
Обычные конфиги очереди и её базы не изменяются. Стенд не читает `.env`.
Каждый запуск создаёт новые топики `parallel-lab-*` и отдельные consumer groups.
Используйте тестовый брокер: стенд создаёт топики, пишет сообщения и намеренно
убивает один собственный процесс в сценарии crash/restart.

## Запуск

Нужны Python 3.13+, POSIX (macOS/Linux), доступный Kafka broker и локальный SDK
с реализацией `processing`. В данной проверке использован настоящий Apache
Kafka 4.1.2 в single-node KRaft, не mock. Клиенту нужны права создавать топики.
TLS/SASL-параметры этот минимальный runner пока не принимает.

Из корня репозитория, в отдельном virtualenv:

```sh
python3.13 -m venv /tmp/kqsdk-parallel-env
/tmp/kqsdk-parallel-env/bin/pip install -e ../kafkaQueueSdk
/tmp/kqsdk-parallel-env/bin/python -m parallel_lab.run_matrix --bootstrap 127.0.0.1:29092 --output parallel_lab/results/run-001
```

Для нестандартного расположения SDK добавьте `--sdk-root /absolute/path/kafkaQueueSdk`.
Для повторного запуска выбирайте новую папку результатов. Один сценарий:

```sh
/tmp/kqsdk-parallel-env/bin/python -m parallel_lab.run_matrix --bootstrap 127.0.0.1:29092 --output parallel_lab/results/run-002 --scenario partitions
```

Все параметры находятся в `scenarios.json`; runner создаёт готовые server-config
для каждой реплики в папке результатов. `results.json` содержит итоги, рядом
сохраняются логи, JSONL-трасса обработчиков и коды завершения процессов.
Ненулевой exit code runner означает провал проверки. Топики автоматически не
удаляются; удалять их следует только на своём тестовом брокере после разбора.

## Режимы

| Профиль | Реплики | Kafka partitions | Локальная обработка | Ordering |
|---|---:|---:|---|---|
| baseline | 1 | 1 | 1 поток | partition |
| threads | 1 | 1 | 4 потока | unordered |
| coroutines | 1 | 1 | 4 корутины | unordered |
| process_threads | 1 | 1 | 2 процесса × 2 потока | unordered |
| process_coroutines | 1 | 1 | 2 процесса × 2 корутины | unordered |
| key_order | 1 | 1 | 4 потока | key |
| partitions | 2 | 4 | 2 потока на реплику | partition |
| hybrid | 2 | 4 | 3 корутины на реплику | unordered |
| ordered_retry | 1 | 1 | 4 корутины, 6 намеренных retry | key |
| rebalance_eager | 1 → 2 | 4 | 2 потока на реплику | partition, range |
| rebalance_cooperative | 1 → 2 | 4 | 2 корутины на реплику | partition, cooperative-sticky |
| crash_restart | 1 → SIGKILL → 1 | 1 | 4 потока | unordered |

Для горизонтального масштабирования реплики используют одинаковую `group.id`,
разные `client.id` и общий входной топик. Kafka распределяет его партиции.
При `ordering=partition` одна партиция остаётся последовательной; `unordered`
позволяет нескольким обработчикам работать внутри неё. `key` сохраняет порядок
ключа внутри процесса; маршрутизация одного ключа в одну партицию необходима
для порядка между репликами. Нельзя раскидывать один бизнес-ключ по партициям.

## Что проверяется

- Сохранность ZIP payload байт-в-байт, Kafka key и исходных headers, включая
  разные `session_uid`, `client`, `entry_id`, metadata и sequence.
- Получение всех уникальных результатов; отсутствие дублей без аварий.
- Финальные committed offsets каждой входной партиции.
- Реальное перекрытие обработчиков и ограничение concurrency в штатных режимах.
- Порядок ключей/партиций, локальный retry, участие всех реплик и процессов.
- Восстановление после SIGKILL и подключения реплики во время работы.
- Штатное завершение по SIGTERM (кроме намеренно убитого процесса).

Гарантия at-least-once: при crash/rebalance дубли допускаются и отдельно
считаются. Дедупликация внешних эффектов по `entry_id` остаётся обязанностью
приложения. Трасса незавершившихся обработчиков при авариях не является
точной метрикой текущей concurrency: запись `end` может не появиться.

Это Kafka → logic → Kafka, а не полный HTTP-клиент → hold → files → gateway
цикл. В этом запуске не проверяются HTTP, PostgreSQL, S3, файловый кеш,
длительная нагрузка, сетевые разделения, падение брокера и репликация Kafka.
Время включает искусственную задержку 40 мс (150 мс для аварийных сценариев),
поэтому это проверка механизма, не production benchmark.

## Что нужно менять в своей очереди

Обновить SDK. Параллельность включается явно блоком `processing`, по умолчанию
поведение остаётся последовательным. Для процессов нужна импортируемая
`process_factory`; см. `parallel_lab.service:sync_factory` / `async_factory`.
Ресурсы бизнес-логики создавайте в factory внутри дочернего процесса.

Для масштабирования на репликах заранее создайте нужное число партиций.
Увеличение партиций существующего топика может изменить маршрутизацию ключей;
делать это во время обработки упорядоченного потока без миграции нельзя.
Hold/aggregator/out-gateway/message-storage не включаются в этот worker pool:
их stateful-адаптация — отдельная задача. Схема БД для стенда не меняется.
