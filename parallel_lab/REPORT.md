# Результаты проверки параллельности — 2026-09-26

Проверена локальная, пока неопубликованная реализация `processing` SDK поверх
master `bcc519e`. Python 3.13, настоящий Apache Kafka 4.1.2, один KRaft broker
на loopback, macOS. Использована общая echo-операция из example/logic.
Настройки и способ повтора: [README.md](README.md).

**12/12 сценариев прошли, 592/592 уникальных сообщений получены.**
Проверены payload, key, исходные headers нескольких сессий и клиентов,
конечные committed offsets, ordering в штатных упорядоченных режимах,
восстановление после аварий. Все штатные процессы завершились кодом 0;
в crash-сценарии первый процесс намеренно получил SIGKILL, новый завершился 0.

\* При авариях незавершённые строки `start` остаются в трассе. Полученный из
такой трассы пик не интерпретируется как фактическая одновременная работа.

В partition-профиле Kafka реально распределил `[0,1]` и `[2,3]` между двумя
репликами; committed offsets `[10,10,10,10]`. При ребалансе один владелец всех
четырёх партиций сменился двумя, финальные offsets `[24,24,24,24]`.
В process-профилях результаты пришли от двух отдельных worker PID.

Дубль при eager-rebalance — проявление at-least-once, а не exactly-once:
между публикацией результата и фиксацией входного offset возможен replay.
Необходима идемпотентность внешних эффектов по `entry_id`. Первый прогон
этого же сценария не дал дублей — редкий исход не исключается успешным тестом.

## Найденные и исправленные дефекты

1. SDK создавал consumers для выходных/event-топиков. На настоящем брокере
   они вступали в группу без application polling. Теперь consumers создаются
   только для явно указанных `in_topics`; добавлена регрессия.
2. Деструктор producer делал `poll(exit_timeout)` даже после успешного shutdown
   flush: тестовые процессы приходилось добивать после SIGTERM. Сетевые
   операции из GC удалены; framework явно flush-ит при остановке. Для прямого
   использования KafkaProducer нужен явный `flush(timeout)`. Добавлена регрессия.

Обе правки не меняют формат сообщений или схему БД. Повторная матрица после
исправлений проверяет коды завершения, а не только наличие результатов.

## Границы вывода

Полный регрессионный прогон SDK после исправлений: **415 passed, 6 skipped**
на Python 3.13 с `KQSDK_TEST_KAFKA_MOCK=1` (132 существующих предупреждения
об устаревшем plaintext auth в тестовых конфигурациях). Дополнительно повторены
оба process-профиля и ordered_retry с явными assertions участия двух PID
и выполнения всех шести намеренных повторов — прошли.

Механизм параллельности работоспособен в проверенных сценариях. Это не
полная production-сертификация: отсутствуют длительный soak, проверка памяти
под большой нагрузкой, сетевые разделения, падение/репликация брокера,
полный HTTP client → hold → files → gateway цикл и кеш. Stateful templates
не переводились на параллельный pool. Синхронный зависший пользовательский
поток невозможно безопасно принудительно остановить — нужна процессная
изоляция и внешний deadline оркестратора.

Исходные артефакты на машине проверки:
`/private/tmp/kqsdk-live-4RACl0/verified/` (results.json, configs, traces,
логи и exit_codes.json). Временный путь не является долговременным архивом;
сводка и воспроизводимые сценарии сохранены в этом репозитории.
Чужие базы, сообщения и конфиги очереди не перезаписывались.
